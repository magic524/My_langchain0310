# metrics_v2 项目流程

## 1. 整体流程

```text
word2md 输出
  -> 构建条款上下文数据集
  -> 解析标签与基线风险点
  -> 做条款级和风险点级评估
  -> 输出 Markdown / JSON 报告
```

## 2. 关键输入

来自 `Contract_Review_System/v2/word2md/outputs_md/<run_id>`：

- `1-原合同.../output.md`
- `2-第三方平台审查结果.../output.md`
- `3-最终审查意见.../output.md`
- `4-采纳情况说明.../output.md`
- 对应 `meta.json`

## 3. 数据集字段

每个合同包含：

- `full_contract_text`
  - 原合同全文 markdown
- `clauses`
  - 条款块和上下文
- `labels`
  - 从采纳情况说明解析出的近似 gold 风险点
- `participants`
  - `third_party`
  - `final_applied`

## 4. 评估输出

每个参与方、每种口径都会输出：

- 条款层指标
- 风险点层指标
- 解释结构分
- 建议可执行分
- 文本同源提示

## 5. 使用边界

`metrics_v2` 不解决以下问题：

- 真正的人工法律真值缺失
- 样本量不足导致的统计不稳定
- 所有文本同源风险

它解决的是：

- 先把当前三份样本跑通
- 让报告更可解释
- 给后续本地 agent 留出稳定接口

## 6. 关于全文输入与分块评分

如果当前测试要求是“合同全文送入模型中，不做任何优化”，建议理解为：

- 推理时：全文输入
- 评分时：按条款 / 风险点归因

这样做的原因：

- 符合当前测试要求
- 同时保留后续诊断能力

否则如果只看整份合同一个总结果，很难知道：

- 模型漏了哪个条款
- 同一条款中的多个风险点漏了几个
- 修改建议究竟对应哪条内容
